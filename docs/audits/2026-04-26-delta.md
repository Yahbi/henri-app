## Findings (delta-only)

Only items introduced by post-baseline code. Issues already noted in the
baseline (LLM injection surface, no CSP, no CI workflow) are not re-listed
unless this session made them worse or better.

### D-1 LOW · Phase 1.6 PDF route shape-cast on `buffer`

`src/app/api/estimates/[id]/pdf/route.ts:172`

```ts
return new NextResponse(buffer as unknown as BodyInit, { ... });
```

The `as unknown as BodyInit` is a TypeScript escape hatch around
`@react-pdf/renderer`'s buffer type. Acceptable as-is — `@react-pdf/renderer`
returns Node `Buffer` and Next 16's `NextResponse.body` types narrowly to
`BodyInit`. **Recommendation**: leave; document in JSDoc when tsc gets
strict enough that this is the only `as unknown as` in the route. Not a
launch blocker.

### D-2 LOW · Phase 2.1 LLM mining cache is process-lifetime only

`src/lib/predictive/llm-mining.ts` uses an in-memory `Map` keyed on the
permit description hash. Cache resets on every Vercel cold start, so a
high-churn batch enricher could re-mine the same descriptions across
invocations. **Recommendation**: when LLM cost becomes measurable, persist
the cache to Redis or a `permit_mining_cache` table. Today the cost is
~$0.0001/call × ~50 contractor permits/day × 30 days = ~$0.15/mo. Defer.

### D-3 LOW · Phase E orchestrator paths lack unit tests

`src/lib/enrichment/orchestrator.ts:659-750` (Phase E branch) has no
direct test coverage. The orchestrator's Phase A-D branches are exercised
via `src/lib/enrichment/__tests__/orchestrator.test.ts`, but Phase E
adds 4 (now 5) parallel branches that all gate on env vars. A test
double using `vi.spyOn(import.meta, 'glob')`-style mocking of the
dynamic imports is heavy for marginal value. **Recommendation**: add
ONE integration test that asserts "with all env vars unset, Phase E
returns the same result as before Phase E shipped". Cheap insurance.

### D-4 LOW · Apollo confidence floor may overcount when source-set is small

`src/lib/enrichment/orchestrator.ts:759-796` (rewritten this session):
the new "3+ ownerSources → 0.95" floor counts source attribution on
`owner_name + owner_first + owner_last` as three distinct sources. If
one source (e.g. `voter_file_fl`) populates ALL three fields, the
attribution map shows the same source three times — but the `Set`
collapses them, so the 3-source floor only fires when three independent
sources contributed at least one of the three fields. **Verdict**:
correctness check passes — re-read confirms the Set semantics. Adding
a test for "single source populating all three fields → 0.95 floor
NOT triggered" would harden against future regressions.

### D-5 LOW · Re-enrich cron doesn't fast-path when migration absent

`src/app/api/cron/re-enrich/route.ts:75-92`: the cron's eligibility
query graceful-degrades when migration 00051 isn't applied (returns
`success: true, skipped_migration_pending: true`). Good. But a separate
risk: if 00051 IS applied but a user's prod env doesn't have
`last_enriched_at` indexed (CREATE INDEX failed silently), the
`NULLS FIRST` index lookup would fall back to a sequential scan on a
~138k-row leads table. **Recommendation**: add `EXPLAIN` to the cron's
debug logs so we can see whether the index is being used. Defer until
the cron has run in prod once.

### D-6 LOW · Provenance chip uses lead.contactSource (not per-field)

`src/components/dashboard/LeadDetailDrawer.tsx:97-105` (new
`ProvenanceChip` component): the chip shows the lead's primary
`contact_source` for both the phone row and the email row, even though
those two fields might have come from different sources (phone from
`numverify`, email from `hunter_io`). The orchestrator carries per-field
`sources` in `EnrichedContact.sources`, but the data isn't plumbed
through `useEnrichment` → `/api/enrichment/property` →
`EnrichmentResult` (the latter is the older property-only type with a
single `source` string).

**Recommendation** (deferred to Phase 2.7): broaden
`/api/enrichment/property` to return `{ sources: Record<string, string> }`
alongside the legacy `source` field, then plumb through `useEnrichment`
into the drawer. Until then, the single-source chip is honest enough —
it represents the LEAD's primary contact source, which is the most
common case. **Severity LOW** because the audit's truthfulness contract
isn't violated: the chip never claims a different source than the data
came from.
